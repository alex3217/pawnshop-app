# Payments and funds-flow audit

Audited 2026-08-01 on `feature/payments-funds-flow-hardening-v1`. No live Stripe calls, database changes, or migrations were performed.

| Requirement | Existing implementation and relevant files | State | Risk and implementation decision |
|---|---|---|---|
| Charge model | Marketplace PaymentIntents in `marketplaceTransactionPayment.service.js` are platform charges. They intentionally contain neither `transfer_data.destination` nor `application_fee_amount`. `payoutRequest.service.js` later creates a separate Transfer from eligible ledger funds. | Partial | Compatibility risk is high if silently converted. Preserve separate charges and transfers in V1 and mark metadata `SEPARATE_CHARGE_AND_TRANSFER`. |
| Server amounts and commission | Reservation in `marketplaceTransaction.service.js` calculates integer cents from the listing, resolves seller-plan commission (Free 1200, Pro 900, Premium 600, Ultra 400 bps), and snapshots gross, fee, seller net, plan, and pricing rule in transaction metadata. | Complete, strengthened | Payment creation now validates the snapshot allocation and sends only safe snapshot metadata to Stripe. Decimal columns remain historical storage; financial calculations use cents. |
| Card data | Web uses Stripe Elements/Stripe.js; `paymentMethods.service.js` returns brand/last4/expiry and Stripe IDs. No production raw-card field was found. | Complete, strengthened | A global post-parser guard rejects PAN/CVC/CVV fields recursively without echoing names or values. |
| Seller bank data | `stripeConnect.service.js` creates Express accounts and `account_onboarding` links, validates trusted HTTPS origins, and stores only account/status flags. Safe display is bank name/type/brand/last4. | Complete | Continue Stripe-hosted onboarding; never add a bank form. Capabilities are represented by charges/payouts flags; detailed capability persistence is absent. |
| Connect ownership/isolation | Account IDs are unique on `PawnShop`; creation metadata binds shop/owner; owner/admin route checks and soft-deleted checks exist. Account-update webhooks resolve by unique account ID. | Complete, strengthened | Payment creation now rechecks listing, seller, and shop ownership snapshot. Inactive account handling remains a payout gate, not a charge-model change. |
| Webhooks/idempotency | Raw Stripe router is mounted before JSON parsing in `app.js`; signatures are verified. Event/object uniqueness and state guards exist across refund, dispute, subscription and connected payout records. | Partial | Core paths are idempotent. There is no single general Stripe-event inbox model, so unhandled event replay observability remains fragmented. |
| Ledger/settlement | `Settlement`, `SellerBalanceLedger`, refund/dispute records, seller payout and connected-account payout records are existing authoritative sources. Ledger entries use integer cents and unique idempotency/reference constraints. | Partial | Do not add a duplicate ledger. Processor fees are settlement-only and not consistently populated from balance transactions for marketplace purchases. |
| Payouts/transfers | Available seller ledger balance is reserved transactionally; shop ownership, approved/nondeleted shop, Connect account, payouts enabled, positive USD cents, duplicate requests and duplicate transfers are checked. Transfers use Stripe idempotency. | Complete with policy gap | The internal “payout request” creates a platform-to-connected-account Transfer; Stripe bank payouts are synchronized separately. UI wording must preserve that distinction. |
| Refunds | Authorized target loading, integer cents, cumulative cap under serializable lock, hashed idempotency, immutable request reason/audit, compensating seller debit, and out-of-order sync exist. | Partial | Existing policy assigns proportional seller-proceeds debit; already-paid funds become `PLATFORM_RECOVERY_REQUIRED`. Transfer reversal is not automated. Inventory restoration policy is intentionally absent. |
| Disputes | Disputes/events are unique by Stripe IDs, out-of-order timestamps are tracked, target status and compensating ledger behavior are implemented. | Partial | Final seller-loss policy is not formally approved; this is an operational blocker for automated allocation beyond current behavior. |
| Subscriptions | Seller/buyer Checkout uses configured price IDs, validates Stripe prices, and syncs invoice/subscription events with event uniqueness. | Complete | Marketplace commissions and subscription revenue remain distinct. No price or product IDs changed. |
| Reconciliation | Existing payout-event synchronization and revenue adapters cover fragments. | Partial, strengthened | Added a read-only deterministic reconciler returning the six required statuses. It never mutates records. A provider-backed authorized batch/API remains deferred. |
| Owner Finance | Existing page exposes Connect readiness, safe payout destination, ledger balance/history, transfers and Stripe payout history with owner-scoped APIs. | Partial | Refund/dispute and commission rollups need a unified owner-safe endpoint. Existing transfer/payout explanatory copy is retained. |
| Super Admin finance | Existing Revenue and Settlements pages expose settlement volume, subscription MRR, commission estimates and editable settlement records. | Partial/high risk | Revenue UI estimates values when authoritative data is absent and settlement editing can alter financial references. Require audit-backed reconciliation before manual changes. |
| Logging/secrets | Morgan logs method/URL/status only; central error logger logs error metadata, not request bodies. Stripe configuration reads secrets from environment. | Complete | Guard response and tests confirm sensitive values are not echoed. Error messages from providers should continue to be sanitized before persistence/display. |
| Permissions | Owner finance controllers use authenticated shop access; admin settlement routes require ADMIN; payment creation checks buyer; refund target authorization exists in controller/service chain. | Partial | Role naming uses both ADMIN and SUPER_ADMIN in different areas. Normalize policy in a later authorization phase. |
| Accessibility/states | Finance pages have loading, error, empty, disabled states and token-based muted/status styles. | Partial | Static review cannot prove contrast. Automated axe coverage is absent; manual light/dark WCAG 2.2 AA certification remains required. |

## Migration audit

Reviewed finance migrations from seller subscriptions through settlement revenue, seller payout ledger, marketplace schema, Connect onboarding, owner payout requests, refunds/disputes, subscription invoice webhooks, connected payout reconciliation, and payment-method consent. Existing uniqueness/index coverage is substantial. No schema change or migration is needed for this hardening slice, and none was created or applied.
